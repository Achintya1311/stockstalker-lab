# C04: F&O expiry-week effect (practitioner claim): diagnosis

See `calendar.md`. **Zero picks on both horizons** (`manifest.json`: `n_picks` 0, `n_dates` 0). The unit
tests pass on synthetic data with `expiry_futstk` filled in, so on the real dataset `_bias_for_history`
abstained on every date. Candidates, in order of likelihood:

1. `expiry_futstk` absent or all-NaN in the cached `data/dataset.parquet` (for example if the cache was
   built before the column was added in 2a21777 and never fully rebuilt, or if the near-month merge
   drops it).
2. `mode_expiry_by_date`'s index and `_pooled_daily_return`'s index not lining up (both are
   `pd.to_datetime(date)`, so this is less likely).
3. One of the two buckets never reaching `MIN_OCCURRENCES` (20 pairs): unlikely over six years.

**Check to run (needs the dataset, so in Actions or a supervised session):** load the parquet and print
`df["expiry_futstk"].notna().mean()` over `has_future` rows for 2015-2020. If it is near zero, the fix is
in `scripts/build_dataset.py` or the cache, not in C04. Not a P1 candidate. Even once it fires, it shares
the calendar family's structural problems (one score per date, alphabetical top five), so its best use is
as a P4 filter input.
